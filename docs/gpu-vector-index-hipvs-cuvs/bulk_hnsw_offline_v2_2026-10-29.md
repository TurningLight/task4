# AMD v2：离线构建与默认启动接入修复

日期：2026-10-29。修复代码提交：`b45d45a7bf17d15c89d05e38c1a5dbb0fb3ad396`。原提测提交：`71e69003169ce5e5dbae3ca2a34681e5789c98dc`。

## 问题边界

原提交在比赛平台仅返回“执行失败、0 分”，没有构建或运行日志。因此不能确认平台实际失败阶段，也不能把本次本地验证等同于平台已通过。

在全新比赛实例的干净检出中，已实际复现：`rust/Cargo.lock` 被忽略且未提交，执行仓库 CI 所使用的 `cargo test --locked --offline -p sql-nio` 会立即报错，要求创建锁文件。另有两个确定的接入缺口：默认 `OB_BUILD_CUVS=OFF`，以及 GPU worker 未纳入 seekdb 默认构建且依赖人工环境变量。这些问题均已修复，但不声称它们已被平台日志确认为唯一根因。

## 本次修复

1. 提交由比赛镜像已有缓存生成的 Cargo.lock，CMake 使用 `--locked`；完整 hipVS 镜像中默认同时启用 `--offline`。没有更改 Rust 1.97.1 的工具链要求，也没有新增 Rust crate。曾用本机较新的缓存生成锁文件，镜像离线验证发现版本缺失后，已换成镜像实际缓存版本。
2. 仅在预装 hipcc、hipVS 头文件/库和桥接库完整时自动开启 `OB_BUILD_CUVS`；普通环境保持 CPU 默认，显式 `OFF` 优先。源码清单 MD5 与 `/opt/seekdb-deps-cache` 完全匹配时才自动复用 C++ 缓存，不覆盖已有依赖目录。
3. worker 成为 seekdb 的构建依赖，生成于同一可执行文件目录，并纳入安装。运行时从 `/proc/self/exe` 对应目录寻找 worker，不搜索工作目录或 PATH；显式路径覆盖保留，显式空值可禁用。
4. 清理 Rust 静态检查问题。请求编号分配改用与原 fetch-update 相同内存序的稳定 CAS 操作，并新增边界/不回绕和多线程唯一性测试；另作空切片匹配、固定长度切片及测试模块位置调整，没有关闭 lint 检查。
5. 镜像没有 PyMySQL。SQL 验证脚本现在随源码附带官方 PyMySQL 1.1.2 的 45 KB 纯 Python wheel、MIT 许可和校验值，直接离线导入；它不是服务器运行依赖。NumPy 使用镜像预装 2.4.6。

GPU 构图算法、M 对应度数、数据精度、采样种子和两种构图策略均保持上一版不变。本次主要解决默认构建/启动和复现流程，而非调低质量要求获取加速比。

## 干净镜像验证

新实例的 13 项 Notebook、辅助代码、样例数据、启动脚本和 hipVS README 与上一实例的 SHA-256 全部一致，没有发现新增 gate 文件。镜像为 seekdb 1.4.0 / ROCm 7.2.4 / gfx1100；CPU 为 AMD EPYC 9334，容器配额 16 CPU、55 GiB 内存，GPU 显存约 48 GiB。

从原提测提交干净检出、应用修复后，只执行：

```bash
./build.sh release --init --make -j8
```

没有手工传 `-DOB_BUILD_CUVS=ON` 或桥接库参数；完整构建成功。日志记录自动匹配缓存、`enabled=ON; worker=ON; offline=ON` 及锁定离线 Cargo 构建。随后直接启动新二进制，实际进程环境中没有 `SEEKDB_HIPVS_BUILD_WORKER` 或 `LD_LIBRARY_PATH`，真实 SQL 日志仍记录了 GPU 构建和原生索引导入。

通过的检查：

- 镜像原生 Rust 1.97.1：5 项 Rust 单测；完整 C++/Rust/worker 构建。
- 本机 Rust 1.99.1、使用从镜像导出的同一套已有依赖：`cargo clippy --locked --offline -p sql-nio --all-targets -- -D warnings` 与 5 项单测。此记录不冒充镜像中未预装的 clippy。
- 5 项构建接入检查：CPU 默认、显式 OFF、缺桥接库时报错、worker 构建依赖及安装、真实 C++ 可执行文件相邻路径发现和迁移。构建依赖夹具使用假 hipcc，仅验证接入；GPU 执行由下方真实 SQL 和 profiler 记录证明。
- 17 项 Python 验证工具测试。
- 默认 GPU 路径及候选自身的 `lib=vsag` 路径：512 行夹具、负数/零/64 位主键、过滤、增删改、20 行 CPU 回退或 CPU 索引、空表首次插入。
- 两个规模各 3 次 CPU 和 3 次 GPU 新建索引，全部通过质量、完整行数、执行计划及构建时间窗口审计。

没有运行缺少依赖/数据库的其他 CI 检查，例如 cargo audit；也没有把 CLA 状态当作编译或性能通过的证据。

## GPU 跟踪与持久化

正式计时后，对同一 worker 二进制分别采集两条策略的 rocprofv3 记录：100k 有 158 条 kernel dispatch、201 条 memory-copy；500k 有 14722 条 kernel dispatch、493 条 memory-copy。记录和 SQL 测量的 worker 哈希一致。

候选随后以 `HIP_VISIBLE_DEVICES=-1`、`SEEKDB_HIPVS_BUILD_WORKER=''` 重启。512 行夹具的持久化/变更检查通过，且 100k、500k 最后一个 GPU 索引的首查询 Top-10 ID 均与重启前完全相同；读取保存的原生索引无需 GPU worker。
